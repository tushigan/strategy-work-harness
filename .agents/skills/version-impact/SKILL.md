# 版本与影响

## 执行契约

- **触发**：任何正文、简报、来源、HTML 手工编辑、设计返回稿、反馈修订、回退、恢复或结项后的新变更都要先做影响检查；只查资料而未改变项目文件时不追加空记录。
- **开始**：先读取真实文件、当前版本、来源、反馈、报告、确认和结项记录，再运行 `python scripts/impact_scan.py --workspace .`；不以 `state.json`、`dependencies.json` 或聊天摘要代替实际文件。
- **产出**：变更文件、直接/间接受影响产出、失效报告/确认/交付/客户决定/结项记录、需要重新走的流程、所需人工授权和当前仍可继续的工作。检查结果要绑定本次实际扫描。
- **停止**：发现文件缺失、摘要与原文指纹不一致、存在未完成写入、对象归属不清或授权范围不清时停止覆盖和下游生成，保留现状并列出恢复或确认动作。
- **交接**：把每个受影响对象交回它原本的 Skill 修订；品牌屋回 `brand-house`，逐字稿回 `proposal-script`，演示稿回 `html-deck`，设计稿回 `design-expression-review`，结项回 `project-control`。本 Skill 只判断影响，不代替这些流程写新内容。

## 判断路径

先区分变化类型，再判断影响，不把所有变化一律当成同样严重：

1. **策略正文、证据或任务简报变化**：相关分析、品牌屋、推导、逐字稿、演示稿、设计简报和设计检核均可能失效；先重做上游，再按依赖顺序重新检核和确认。
2. **只改 HTML 样式或布局**：不自动判定策略正文变化，但必须重新回读实际 HTML、显示和版本绑定；若编辑同时改变文字，则按正文变化处理。
3. **来源、原文或来源指纹变化**：重新检查引用、反证、结论强度和跨项目越界；同版新报告也不能自动继承旧确认。
4. **设计返回稿变化**：保留旧提交和报告，登记新提交，重新逐页检查；不能只替换文件名或复用上一版红黄绿结论，不沿用旧报告。
5. **回退或恢复**：回退本身也是新版本，保留旧版本、黄灯、反馈、修订次数和原决定；恢复不能恢复旧批准或绕过当前授权。

执行顺序是：保留旧版本 → 扫描并记录影响 → 取得需要的对齐授权 → 从最上游变更点重新修订 → 按依赖顺序独立检核 → 重新确认 → 刷新结项状态。最多两轮自动业务修订仍未通过时交人工；额外一轮必须绑定上一轮记录，不换作者或清零计数。结项后运行 `python scripts/project_closure.py refresh --workspace .`，新变更不能覆盖原结项记录。

## 字段含义

- `changed_files`：字节改变或缺失的实际文件。
- `affected`：直接和间接受影响的产出及重做步骤。
- `invalidated_records`：需要失效并重做的报告、确认、交付、客户决定和结项记录；历史只保留，不删除。
- `affected_workflows`：受影响的交付、确认和结项流程；即使正文没换版，同版新检核也可能使旧确认失效。

文件系统不提供独立身份认证，主控必须实际调用未参与写作的 fresh 检核实例。`--record` 只在本次影响结果需要进入项目记录时使用，连续状态无变化不重复追加；空白项目不写示例记录。
