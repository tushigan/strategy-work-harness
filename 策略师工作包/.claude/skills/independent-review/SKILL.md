# 中立检核

检核者必须读取原始任务、验收标准、来源证据、上游版本和实际产出。报告写明产出版本、检查范围、结论、证据定位和未覆盖项。

作者与检核者必须是不同执行实例。检核者不直接修改被检产出后再批准自己。红灯表示明确违反策略或严重误读，黄灯表示可商榷或需要补证据，绿灯表示在检查范围内成立；个人审美偏好不能直接判红灯。

最多自动修订两轮；第二轮后仍未通过就保留各版本和争议，交策略师决定。

合同、排期和 Excel 的实际报告格式及命令见 `运行环境与命令.md`。报告必须绑定当前版本、原件、上游和实际文件；Excel 还要评估全部渲染图，并写清可读性问题或未验证限制。
独立业务检核不是代码审查；自动化测试中的模拟确认也不是策略师真的批准。

## 简报、研究与品牌屋

主控用 `phase3.py review-sources` 生成必要文件列表。检核实例完整读取列表内 JSON、Markdown、任务合同、上游原文及反馈；长资料分批读取，不接受作者摘要替代。列表和指纹只能核验覆盖，不能替代内容判断。

正式产出包括简报、研究准备、证据、分析、品牌屋、独立推导及总控 `summary`。按上游顺序检核，通过后主控登记；依赖未通过不能给下游放行。作者实例必须为实际执行者，不通过换角色名称回避自审。

报告字段及命令见 `策略与品牌屋运行说明.md`：精确 `target`、真实 `reviewer_instance`、`status`、章节 `scope`、`assessment` 五项判断、`findings`、`uncovered`、实际读过的 `checked_sources`。真实 Agent 对合成资料的判断为 `simulation:false`；只有程序模拟报告为 true。合成案例本身仍需明确标注，人工测试确认必须另标模拟。

状态仅为 `passed/passed_with_yellow/returned/insufficient_evidence`。有黄灯必须附黄灯通过，有红灯、关键原文未读或范围未覆盖不能通过。重点检查事实与意见是否混用、反证是否保留、消费者利益是否有推导、使命愿景价值观是否各自成立，以及现有能力与待建设项是否分开；不要求模仿总监措辞。

每次修订重新检核，最多两轮自动业务修订，人工反馈次数另记。上游变化、旧版批准或作者自审不能放行；额外轮次必须有明确决定且累计保留原轮次。检核者只写报告，不改稿、不确认、不更新项目总状态。

## 跨阶段与总控

总入口为 `python scripts/review_gate.py inspect --workspace .`，复用各阶段实际门禁，不把一次总检查当作新的通过报告。来源资料不是可批准的正式产出。

项目汇总、外部任务交付登记、结项报告使用 `control_artifacts.py`。主控先 `sources` 提供完整来源及章节，检核者写与提案检核同类的五项实质判断、红黄绿意见和未覆盖清单，`target` 使用 `control` 完整引用。任何历版作者都不能检核该产出，不能将作者改名替代 fresh 实例。

结项报告须检查每个合同列项对应的实际交付、任务、报告、策略师和客户确认原文；有未交付产品战略或未客户确认就不能结束。检核只判断记录与业务依据，不伪造客户身份或同意。

## 提案、演示稿和设计返回稿

逐字稿、HTML 品牌屋和演示稿各自独立检核，不能共享一份通过结果。按相应 Skill 取得全部原文、精确上游、实际文件与必要的逐页视觉证据。

设计返回稿先由 design-expression-reviewer 提出诊断候选；你须是不同的 fresh independent-reviewer，完整读取原件、当前简报、来源、逐页画面及候选诊断，重新作判断，而不是给诊断自报盖章。最终报告使用 design-expression-review 的现有 design-review 格式，写你的真实执行实例，由总控回读登记。此处不增加审批接口，也不能把通过当客户批准。

检核报告是检核证据，不递归要求报告检核自身。无法使用真正独立实例时明确待检，不以作者改名代替。

## 执行契约

- **触发**：任何正式候选产出准备进入策略师确认、客户交付、下一阶段生成或结项时触发；普通草稿不强行登记正式报告。
- **开始**：列出本次完整检查范围、原始依据、上游版本、实际文件和独立性排除项；缺一项先标资料不足。
- **产出**：报告逐项写结论、证据定位、未覆盖项、状态和下一动作。`passed`、`passed_with_yellow`、`returned`、`insufficient_evidence` 只根据实际证据选择。
- **停止**：原文未读全、实际画面未看、版本或指纹不一致、作者参与检核、红灯或关键范围未覆盖时不能通过。
- **交接**：报告交主控回读；主控再请策略师确认或按报告回改，不由检核者直接改稿或更新公共状态。

## 本版效率与增量规则（适用时优先于上文完整读取的通用措辞）

日常续做只运行 `python scripts/project_handoff.py resume --workspace . --json`。它只读记录，核对当前任务、来源、记忆、有效分派及代码/双宿主完整性；默认输出摘要，省略数量明确显示，需展开用 `--details`。当前错误不能靠摘要隐藏；它不是正式移交通过。正式移交保留 `inspect/prepare/accept` 的全量清单检查，不将 Hook 的结构提示当业务验收，不在只读启动中使用 `--refresh` 或 `--record`。

独立任务、简报、研究准备/证据/分析、品牌屋正文/HTML、推导、正式逐字稿及演示稿支持第2版报告协议：首次建立完整基线，此后默认计算累计差异；当前版本和报告有效且未变化直接复用，最终交付核对完整覆盖链，不因用途为final强制全文重读。规则及空白模板见 `.agents/skills/independent-review/references/增量报告协议.md`、`.agents/skills/independent-review/templates/增量报告.json`（Claude 对应同技能目录）。合同/排期、设计返回稿及总控产出仍按原门禁检查。

基线必须绑定同任务完整报告、不可覆盖的全部来源快照、版本、项目记忆及独立性排除项。当前文件重新核对指纹；增量计划由 `incremental_review.py` 计算累计差异。检核者读取 `checked_sources_required` 的真实原文及成品，逐项核实实际影响；`reused_coverage` 单列继承覆盖，绝不写成这轮已读。CLI 默认 `--change-kind unknown` 扩大检查；仅在独立者有依据判定纯局部措辞时使用 `local_text`。不得仅据作者标签缩小范围。

来源、数字/单位、策略意思、记忆或上游变化扩大来源复核；范围不明也扩大。HTML/PDF 新版的视觉检查按页增量（v1.7.0，W01）：程序在同一渲染环境下逐页无损截图、按像素逐个比对上一份通过检核所绑定的版本，像素完全相同的页继承上次视觉结论（记“继承视觉覆盖”，不写成本轮已看），其余页必看；没有基线、旧报告无像素指纹、环境不同、字体未加载、页面脚本改变、渲染不稳定（动画等）一律必看，页数变化从第一处不一致起其后全部必看，阶段首次检核仍全页。对外交付前（final）视觉部分同样只看变化页。来源与数字的原文覆盖仍按文件级规则，不因视觉继承缩小。正式演示稿仍运行 deck-browser-check 并绑定本次真实截图、导出重开与离线结果。没有真实渲染不得声称视觉通过；合成只用于 test_mode 测试。

增量报告是新的独立判断，不继承通过、人工确认或客户批准；仍禁止任何历版作者及诊断者自审。上一轮独立者可继续审未参与创作的修订，角色名不证明独立性，主控须保留真实实例证据。两轮自动修订上限、当前确认及原有门禁均保留。历史旧报告只按旧完整格式回读；新登记的独立任务报告必须使用第2版格式。当前HTML/PDF放行均须绑定当前成品逐页视觉证据（必看页实看 + 程序比对的继承页），不得以旧格式绕过。后续退回、证据不足、撤销或新的完整审核会使旧基线失效；纠正问题后完整独立重审建立新基线，不接受作者自填已解决。继承覆盖保留未解决黄灯意见；没有保存的有效基线不能事后伪造继承。


## 累计检核与冻结审查组（本节优先于旧全文/新实例措辞）

先运行 `python scripts/incremental_review.py --workspace . --target 目标JSON --reviewer 实际独立实例 --purpose revision --json`，final用 `--purpose final`；不再要求手动找base-record-id。首次无有效基线返回full；以后默认累计改动和关联影响。unknown保守扩大；独立者已有充分依据判定局部文字时用 `--change-kind local_text`。dispatch_required=false 时直接回读当前报告和覆盖链，不再派审或生成新报告。确认仍核对当前版本，不继承旧批准。若复用依据失效，按返回范围重新检查。

检核请求带 review_target、simulation、change_kind及review_purpose，agent_dispatch.py prepare 会重新计算计划：未变化返回reused且不新增分派；需要审查时 input_files 必须精确对应实际 required 范围，另传完整任务原话与标准。基线/差异/未解决意见只作必要证据引用，禁止复制整段聊天历史或递归审查报告。角色文件仅定义职责；按宿主实际可用能力调用，复用未参与创作的实例时不携带无关聊天。

较大任务且额度允许时，用 `shencha_zu.py create --workspace . --input 组请求JSON --actor 主控` 建2—3名只读组，成员含member_id、role(part/consistency)、scope、paths；唯一consistency成员读取全部本次相关部分以独立判断跨部分一致性。目标绑定冻结版本。create可能直接返回dispatch_required=false。通过 request 动作取得成员最小请求，再用现有prepare/assign/return/complete；使用真实不同执行及宿主实例和调用证据，每份报告另存不可覆盖路径。组内同任务并发仅在冻结计划校验后允许，普通同任务拦截保留。

成员报告包含 target、reviewer_instance、simulation、status、scope、checked_sources、assessment、findings、uncovered；实际读过的原件必须等于成员分工，consistency还须有assessment.cross_consistency文字判断。独立报告与实际调用/返回/回读证据绑定。组 submit 保存每份报告，失败/缺口照实存；merge检查覆盖、意见冲突、独立身份及当前版本，并调用原生登记。合并模板提供原生格式所需的当前视觉证据等字段，不能自行填写另一个通过结论。漏查、失败、冲突、重复实例、来源/记忆变化或中途换版全部阻断；保留原报告，重新核对后建新组，不能删除并发拦截后直接放行。

实际checked_sources、继承reused_coverage、uncovered分别记录。scope列出整条覆盖链的业务章节，不能把继承原文说成这次已读。来源、数字、策略和不明影响扩大；HTML/PDF新版本须有必看页的实际视觉证据，其余页只能是程序按像素比对给出的继承页（v1.7.0，W01）。修订上限、真实来源和当前确认保持。日志从原生计划/分派/返回/合并节点生成模式和原因，无额外逐步日志工具调用。本候选仅作者自测。
