# 项目工作区使用说明

## 第一次启动

先运行启动检查，再填写 `project/state.json` 中的项目标识。空白模板不预填客户、品牌、人员、日期或合同内容。

策略师把合同服务列项文件放到 `project/inputs/`，由项目内 `contract-schedule` 技能读取，先确认识别范围，再形成计划。操作入口见根目录 `运行环境与命令.md`，不会自动创建项管系统任务。

## 每次继续工作

1. 在工作包根目录运行 `bash .codex/hooks/validate-project.sh --json`，先处理结构错误，再开始本地工作。
2. 先读统一恢复报告中的 `workflow_snapshot.project_memory`、`standalone` 和 `task_receipts`。已有合同或排期记录时运行 `python3 scripts/workflow_status.py --workspace . --refresh`，重建并查看 `state.json` 的 `next_action`；空包不为示例写状态。
3. 已有任务计划时运行 `python3 scripts/phase3.py status --workspace . --refresh`。核对到期任务、前置成果和待对齐版本；不会自动改承诺日期或创建重复任务。
4. 将新材料或反馈交给 Agent。由 Agent 完整读取、起草并登记版本，再交另一个实例检核；不要求策略师手写 JSON。
5. 有逐字稿、演示稿或设计提交时，Agent 运行 `python3 scripts/phase5.py status --workspace . --refresh` 核对版本、任务、最新检核和内部确认；`impact-scan` 同时列产出及设计提交状态。此命令会刷新当前项目缓存，空包不为示例执行；状态检查不替任务验收。
6. 已初始化项目再读 `review_gate.py inspect`、`impact_scan.py --record` 和 `project_closure.py inspect/status`，命令均指定 `--workspace .`。交付、客户决定和结项按 `项目检核与结项运行说明.md` 分别记录；不要直接改缓存为完成。

## 独立任务

会议跟进、临时 Brief 或同事交接可以不依赖合同计划。主控先登记最小项目身份，再按根目录《运行环境与命令.md》的独立任务入口登记原话、来源、进度、成果和下一步。继续工作时读取 `workflow_snapshot.standalone`、`project_memory` 和实际文件，不能只读 state.json；正式任务状态与独立任务分别保留。独立任务成果由另一实例绑定当前版本检核；用户直接要求 PPT 时，不自动强制补正式提案的逐字稿前置。

人物称呼、品牌名、固定口径和项目边界等明确纠正由主控写入本工作包的项目记忆。旧值、修订原因和来源都会保留；推测或待确认内容不能写成已确认。Brief→PPT 等关系绑定具体版本，上游换版会提醒下游重新对齐。外部动作的成功、失败或结果未知分别保存回执，结果未知时先核对，不盲目重试。

## 内容工作

每个任务先有简报，设计任务另加策略师视角的转换清单，不代设计师决定构图和字体。调研先有访谈与采集准备，线下采访和观察仍由人完成。来源归档后形成证据稿、分析，再起草品牌屋正文及独立推导。

策略师只需提供文字反馈，或音频加可靠转写稿。Agent 先定位任务及版本，能够唯一识别就直接改稿，不能识别才提问；保存旧稿、修改原因及少量启发问题。音频可保存不代表已听取或已转写。

主控显式调用 strategy-author 写简报、研究和品牌屋候选，回读登记后交不同的 independent-reviewer。研究分析以及品牌屋正文和推导需要策略师明确的内部确认才能完成相应任务。独立检核通过不是人工确认，更不是客户批准。上游变动会使下游待对齐，旧确认不能给新版放行。详细命令、格式和恢复方式见根目录 `策略与品牌屋运行说明.md`。

## 提案和设计返回稿

通过 Codex 说“为这个内部提案任务起草完整逐字稿”：Agent 先检查本任务简报，以及计划前置任务中同一任务的品牌屋正文和推导；简报须检核通过，正文和推导还须策略师内部确认。proposal-author 写完整、连贯、可以直接念的稿件，主控登记后交 fresh independent-reviewer 全文检核，再请策略师明确确认或退回。

确认逐字稿后再说“按已确认逐字稿生成 HTML 演示稿并逐页检查”。演示稿单独检核、单独确认；浏览器文字编辑和导出重开只保留草稿，要采纳时请 Agent 回到逐字稿生成新版。新版或新报告会使旧确认失效。初稿后两轮自动修订即停止，人工明确追加一轮才能继续，历史轮次保留。

说“检查并启动这个内部提案任务”时，主控用 `task-start` 核对有效计划、开始日期、本任务简报以及前置品牌屋任务的有效完成记录，后者包含 HTML 检核。逐字稿与演示稿分别检核并确认后，再用 `task-complete` 记录内部提案完成。客户确认、产品战略和包装不能由该接口凭简报标完成。

收到设计师稿件时说“按这个设计任务的当前简报检查这份稿件，逐页给出证据和红黄绿意见”。design-expression-reviewer 先写诊断候选，再由不同的 independent-reviewer 重新看原件、简报、全部来源及每页画面并写最终报告。简报绑定版本引用，不是文件路径引用；PNG/JPG 真实解码，PDF/PPTX 还须实际打开或渲染每页，旧 `.ppt` 请人工转 PDF/PPTX。缺字体不能靠解析自动识别，应在视觉核查中观察并记录限制。详细步骤与报告格式见根目录 `提案与设计检核运行说明.md`。

## 外部能力

飞书和云端大脑已有本地受控适配，实际账号、权限和线上读写须另外核实。按根目录 `外部连接说明.md` 和项目内技能授权后使用，状态只写真实结果。资料未取得时继续本地工作，不编造信息；回传结果不明先核对，不重复发送。

## 记录位置

记录格式和允许的状态值见 `project/records/README.md`。所有路径从工作包根目录计算；需要移交时直接复制整个工作包，不依赖原电脑的聊天历史或浏览器缓存。
